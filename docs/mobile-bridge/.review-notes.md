# Working notes (not the deliverable) - crypto review of mobile proposal v1

Verdict: accept the X25519/HKDF/XChaCha20-Poly1305 + QR/SAS + KK-style scheme, with these changes:

1. **Unauthenticated 403 device_revoked -> phone drops pairing** = network attacker can wipe pairings (plaintext outer status).
   Fix: /session returns an authenticated revocation notice: AEAD(HKDF(DH(e_h? no) DH(S_h, e_c), salt=SHA256(label|deviceId|e_c), info="aiondx/v1/revoked"), {deviceId, ts}).
   Host can compute without S_c (deleted on revoke). Phone only auto-forgets on a verified notice; unauthenticated 403 -> "PC refused", keep pairing, manual Forget.
2. **Pairing: one QR, first-valid-request locks it.** Second valid request with a different devicePk -> abort pairing, PC warns "code seen by another device". Re-POST polling must re-seal with fresh ts (2 min skew vs slow user approval). Bind pair response to request: add SHA256(request ct) into response AAD (optional hardening).
3. **Handshake init replay** (within ±2 min) -> host creates junk sessions (memory DoS, no key compromise). Fix: host caches seen epk for 5 min, rejects duplicates; cap sessions per device (e.g. 4, evict oldest).
4. **Retry/failover vs replay window**: same envelope retried to 2nd URL after host processed -> rejected as replay -> client can't tell if a mutation happened; 401 re-handshake retry of a non-idempotent POST can double-send if 401 injected.
   Fix: inner request carries `rid` (client UUID); host dedupes mutating requests per device for 10 min; host caches sealed response per (sid,seq) within window and returns it for an exact duplicate envelope.
5. **Per-PC device keys** (multi-PC): generate a fresh S_c + deviceId per paired host instead of one phone identity. Independent revocation, "Forget PC" on phone is cryptographically final, no cross-PC linkability, one PC's DB leak doesn't expose the phone key used elsewhere (public anyway, but deviceId correlation). Client change: identity lookup keyed by hostId (SecureChannel already takes identity+host together).
6. **Path allowlist** on the RPC dispatcher: phone-as-user is legit, but raw passthrough of {method,path} to the whole API gives a stolen/compromised phone RCE (shell routes, MCP server config = arbitrary command, file ops, settings). Allowlist mobile routes only. FLAG for sign-off.
7. **Never expose main aioncore API on LAN.** Separate listener (LAN-bound) serving only /api/mobile/v1/{hello,pair,session,rpc}; dispatch in-process into the router with a Mobile principal. Windows firewall rule Private profile only.
8. Clock-skew error should return host time so phone can explain.
9. Biometric: client-only flag is theater. Real enforcement = confirm key (32B) delivered inside the approved pair response, stored by phone in expo-secure-store requireAuthentication:true; sensitive inner requests carry `confirm = HMAC(k_confirm, canonical(sid,seq,method,path,sha256(body)))`; bridge verifies. Expo-only, no native module. Android biometric re-enrollment invalidates -> "re-confirm on PC" flow.
10. SAS grinding: attacker with QR photo can't target victim's SAS (needs DH secret) -> 1e-6 per attempt, and lock-on-first means one attempt. OK.
11. FS check: ikm includes DH(e_c,e_h) -> statics leaking later doesn't expose past sessions. OK. KCI if S_h leaks -> out of scope (PC compromise).
12. Manual-entry deferral: agree.

# DESIGN DIRECTION (decided so far, to write into contract)
- Delivery: core patch `core-0006-mobile-bridge`, new crate `aionui-mobile` in aioncore (RustCrypto x25519-dalek, chacha20poly1305 XChaCha, hkdf, sha2). Own LAN listener (default port TBD, configurable, QR carries it), serves ONLY /api/mobile/v1/{hello,pair,session,rpc}. Main API stays 127.0.0.1. Firewall rule Private profile only.
- Inner API = mobile FACADE /v1/... (allowlist by construction), handlers call domain services directly with user_id + Principal::MobileDevice{device_id} (audit). Not raw passthrough.
- Desktop admin routes (behind normal auth, localhost): pairing offer create/QR, pending list w/ SAS, approve/reject, devices list, revoke. WS event mobile.pairingRequested. Renderer UI via AionDX renderer patch.
- Message sync: bridge change journal (epoch + monotonic rev) fed from event bus (message.stream finish/userCreated/statusChanged/turn.completed); GET .../messages?since_rev= -> changed msgs; stale/unknown epoch -> {reset:true}. Backward paging = wrap existing before-cursor.
- Approvals: bridge tracker of pending confirmations across convs (from message.stream acp_permission/ask + confirmation.remove, reconciled via per-conv /confirmations; seeded from teams' pending_confirmations). Answer = {decision: allow_once|allow_always|deny | option_value | answers} mapped per backend (ACP option ids by kind, session allow/allow_always/reject, aionrs {value: proceed_once|cancel}+always_allow).
- attention signal per agent/conversation: needs_approval | needs_answer (confirmation.questions != null) | your_turn (idle, last visible agent msg newer than user's last_read) | none. Plain-text questions not detectable - say so.
- Unread: per-user last_read in client settings KV `aiondx.read.<convId>`; POST .../read. Desktop renderer doesn't write it in v1 (follow-up).
- wake = POST attach (+ optional nudge message). shutdown = polite (new: user-initiated shutdown_request via session) ; force = DELETE agents/{slot} hard remove (needs confirm proof).
- Decisions draft: (1) accept scheme w/ fixes 1-9 above; (2) /api/mobile/v1 on separate port + mDNS _aiondx._tcp opt-in (TXT v=1, hid prefix); (3) LAN-only v1, BYO Tailscale/WireGuard via extra URLs in QR, no hosted relay (conflicts with no-telemetry stance - Nathan's call); (4) host key: DPAPI-protected file in %APPDATA%\AionUi\aiondx-mobile\ (or Credential Manager); paired devices table in aioncore DB; per-PC phone keys; revoke on PC = delete row + kill sessions; phone Forget = delete per-host key; (5) 12h absolute + 30 min idle; (6) facade schema; (7) bridge-enforced confirm HMAC with biometric-gated k_confirm for: approvals, spawn, shutdown/force-remove, revoke; NOT for chat send (flag).
